# Auditoría PayRam 3.9.0 — 2026-10-20

## Alcance y método

- Imagen `payramapp/payram@sha256:1181cd5d886a50d68565c275dad231d9a1d75735dca3ce5873f334c2f9db3791`.
- Descarga completa, `docker export` y extracción de rootfs (2.9 GB).
- Inspección de:
  - `/startup.sh`, `/etc/supervisor/conf.d/supervisord.conf`, `/etc/nginx/*`, `/config_*.yaml`.
  - Binario Go `/payram` (75 MB, Go 1.26.3, **no stripped, con debug_info**).
  - Build de Next.js `/web/.next` (61 MB, sin source maps).
  - SBOM SPDX (4.046 paquetes) y procedencia SLSA.
- Cruce del SBOM contra OSV (`api.osv.dev`).
- Prueba runtime con PostgreSQL externo, Redis, nginx, PayRam core/web y el overlay.

## Hallazgos confirmados

### CRÍTICO — Next.js 16.2.6

- `GHSA-2xp9-vwfh-vxw4`: RCE no autenticado en `/_next/image` (AVIF). Fixed 16.3.3.
- `GHSA-vcvr-r3jv-pc5j`: RCE en `next/og` ImageResponse. Fixed 16.3.6.
- `GHSA-p293-qw3h-jr36`: RCE en Windows. Fixed 16.3.3 (no aplica a Linux).
- Altos: SSRF en Server Actions, SSRF en Image Optimization, middleware/proxy bypass, DoS.
- **Mitigación runtime**: Caddy y nginx bloquean `/_next/image`, `/api/og`, `/opengraph-image`, `/twitter-image`, dev endpoints y `/swagger`.
- **No es un parche**: el código sigue siendo 16.2.6; los CVEs de Next no desaparecen.

### CRÍTICO — Core cerrado y sin firma

El repositorio `PayRam/payram-core` no es público (404). La imagen no está firmada. La procedencia SLSA es un registro de BuildKit, no una firma del publisher. No se puede demostrar ausencia de backdoor.

### ALTO — Postgres interno con credenciales por defecto

`startup.sh` crea el rol `payram` con contraseña `payram123`, escucha en `0.0.0.0` y `pg_hba` permite `0.0.0.0/0 md5`. El overlay:

- Reemplaza la contraseña por `INTERNAL_POSTGRES_PASSWORD` (≥24 chars).
- Cambia `pg_hba` a `127.0.0.1/32 scram-sha-256`.
- Cambia `listen_addresses` a `localhost`.
- Si `POSTGRES_HOST` es externo, **omite el bloque de Postgres interno** y elimina `[program:postgres]` de Supervisor.

### ALTO — Payouts auto-aprobados por USD 25.000

`config_production.yaml`: `autoApproveEnabled: true`, `autoApproveAmountInUSD: 25000`, `otpThresholdInUSD: 2000`, `dailyLimitInUSD: 100000`, `hourlyLimitInUSD: 25000`.

El overlay escribe `false`, `0`, `0`, `1000`, `500` (semilla). En una DB ya inicializada hay que ajustarlo también en el dashboard.

### ALTO — CORS abierto por defecto

Log de PayRam: `CORS: no PAYRAM_ALLOWED_ORIGINS set, allowing all origins`. El compose define `PAYRAM_ALLOWED_ORIGINS=https://${PAYRAM_DOMAIN}`. Verificado: el warning desaparece.

### ALTO — Updater oficial root

`setup_payram.sh` descarga y ejecuta `setup_payram_updater.sh` desde GitHub como root. El overlay no lo instala; el gate busca artefactos. La UI de Next también muestra el `curl | sudo bash`; el overlay reemplaza ese texto.

### MEDIO — Secretos en DB

`jwt.access.secret` y `jwt.refresh.secret` se guardan en claro en la tabla `api_keys` (con hash adicional). No se puede cambiar sin código; la DB debe tener password fuerte, red aislada y backups cifrados.

### MEDIO — Clave efímera en logs

PayRam imprime `Generated Key: <64 hex>` en `/var/log/payram-core.out.log`. No aparece en la DB y cambia en cada arranque, pero es un secreto en logs. El overlay lanza un redactor local que la sustituye por `[REDACTED]` (verificado en runtime).

### MEDIO — Redis root y daemonize

Redis corría como root y con `daemonize yes`; Supervisor lo marcaba FATAL. El overlay:

- `user=redis`.
- `daemonize no`.
- PID file en `/var/lib/redis/redis-server.pid`.
Verificado: `redis-server RUNNING` y proceso como `redis`.

### MEDIO — Endpoints dev/preprod en el build

`develop.payments.betora.vip`, `preprod-wallet.resuefas.vip`, URLs Vercel dev/preprod y el comando del updater estaban en 8 archivos de `.next`. El overlay los reemplaza por endpoints de producción/`wallet.payram.com` y elimina el comando del updater. Verificado: 8 archivos modificados y sin marcadores prohibidos.

### MEDIO — Telemetría

- `SENTRY_DSN` configurable; el overlay lo deja vacío.
- MetaMask SDK analytics por defecto (`mm-sdk-analytics.api.cx.metamask.io`); el overlay reemplaza el fallback por `http://127.0.0.1:9/`.
- `ipwhois.app` se usa server-side para geolocalización; no se bloquea para no romper funciones de país.

### INFO — `os/exec`

El binario importa `os/exec`; el análisis de llamadas muestra que se usa en `SystemServiceImpl.GetAllWorkerStatuses` y `runSupervisorctl` para `supervisorctl` (argumentos fijos). No se encontró shell con input de usuario.

### INFO — Sin malware evidente en lo inspeccionado

- Sin archivos setuid (`find -perm -4000` vacío).
- Sin claves SSH, `authorized_keys`, cron sospechoso ni binarios en `/tmp`, `/root` o `/home`.
- Sin mineros/reverse shells por nombre.
- PNG de tokens sin bytes después de `IEND`.
- No se auditó el binario Go completo ni cada byte de `node_modules`; no se puede afirmar “limpio”, solo “sin indicadores en lo revisado”.

## Runtime verificado

Health 200, DB ok, 14 workers RUNNING, sin `postgres` interno, `redis-server` RUNNING. `/`, 200; `/swagger/`, 404; `/_next/image`, 404; `Generated Key: [REDACTED]`.

## Conclusión

El overlay elimina defaults peligrosos, bloquea la superficie conocida, desactiva telemetría y endurece red/Redis/CORS/payouts. **No convierte la imagen cerrada en una imagen parcheada**: Next.js 16.2.6 y los CVEs de Go/Next siguen presentes. Para mainnet con fondos reales se necesita un rebuild del proveedor o asumir el riesgo de forma explícita.
